# Style Rules

## 核心取向

- 先判断归属，再写代码。
- 先判断归属，再收缩对外边界。
- 抽象要形成职责类，不接受局部函数套帽。
- 反对防御性冗余。
- 大类只保留入口、协调、生命周期。

## 归属规则

- `ProgressClass` 这类单条视图，应跟随条目对象。
- 汇总 badge、展开控制、总状态，应归面板级控制对象。
- `Manager` 不应同时管理条目构造、动画、badge、下载、状态同步。

## 坏味道判定

- 一个私有方法引用多个其他私有方法。
- 一个类里出现一屏私有方法，且大多只彼此服务。
- 一个逻辑链只是被拆成 `_start_xxx` / `_finish_xxx` / `_sync_xxx` / `_do_xxx`。
- 同一语义被写成字段级手工同步，而不是对象级替换。
- 已有按钮启用状态，还在槽函数里继续判空。
- `__init__.py` 或 facade 模块导出一大片符号，但包外真实调用很少。
- 已有稳定 owner 对象，还再包一层 `get_xxx` / `set_xxx` / `clear_xxx` / `build_xxx` 转发。
- 单行函数只是换名字转发到另一个公开方法、公开类或公开实例。

## 处理原则

- 单次使用、逻辑短：内联。
- 单次使用、逻辑成体系：抽独立 controller。
- 多对象之间关系稳定：直接建立明确的拥有关系。
- 替换语义明确：整体替换，例如 `deepcopy`，不要一串赋值。
- 不要为布尔默认值或单个参数差异新增成组单行包装方法；优先保留一个主入口，把差异收成显式参数。
- 拆文件先收缩外部 API；只导出已有调用或明确稳定的领域概念。
- owner 已明确时，让调用方直接依赖 owner，不额外补 facade wrapper。
- 单行函数没有独立领域语义时，内联或放回 owner 内部，不提升成公共接口。

## 输出要求

- 先改结构，再说细节。
- 不要等用户逐个指出，再逐个清理。
- 重构后类边界必须清楚，职责名必须直接。
- 重构后对外导出边界也必须清楚，`__init__.py` 不能成为旧单文件的搬运层。

## 演进规则

- 当用户明确表达新的稳定偏好时，把规则追加或改写到这里。
- 新规则优先写成约束句，不写长篇解释。
